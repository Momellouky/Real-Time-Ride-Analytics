1. Product overview

The project is a local demo application that simulates a simplified ride-hailing operational dashboard. Its primary purpose is to provide hands-on experience with Apache Pinot as a real-time analytics database, using Kafka as the ingestion layer.

The application contains two Vue.js pages:

  • Analytics Dashboard — visualizes the latest metric values and how each metric changed during the last hour.
  • Metrics Settings — allows the user to manually change metric values and submit a new complete system snapshot.

The project intentionally avoids production concerns such as authentication, multi-user coordination, complex domain workflows, and a transactional relational database.

2. Goals and non-goals

Goals

  • Learn how Kafka streams data into Apache Pinot.
  • Learn how Pinot supports low-latency analytical queries over recently ingested data.
  • Visualize real-time metric changes from a Vue.js dashboard.
  • Build a small FastAPI layer for ingestion validation and analytics querying.
  • Practice historical time-series queries, especially for a rolling one-hour window.
  • Keep the architecture simple enough to understand every component end to end.

Non-goals

  • No authentication or authorization.
  • No real driver or rider accounts.
  • No real ride lifecycle management.
  • No payment, pricing, routing, or geospatial ride matching.
  • No PostgreSQL or other transactional database.
  • No production deployment, high availability, or advanced security hardening.
  • No multi-zone support in the first version.

3. Target user and use case

The only intended user is the developer operating the demo locally. The user changes operational values from the Settings page and immediately observes how the Analytics Dashboard reacts after the new event is ingested into Pinot.

Primary learning loop:
Change a value → FastAPI validates it → Kafka receives a snapshot event → Pinot ingests it → dashboard polling retrieves updated analytics → UI reflects the change.

4. Metrics in scope

Online Drivers Number of currently online drivers.
Ride Requests Current total ride requests represented by the submitted snapshot.
Accepted Requests Current number of accepted ride requests.
Cancelled Requests Current number of cancelled ride requests.
Drivers Waiting Number of online drivers currently waiting in the configured zone.

Only one logical zone is used in this project, but every event must still include a zone_id so that the data model remains extensible.

6. Frontend requirements

6.1 Technology

  • Vue 3
  • Vite
  • Chart.js or a lightweight Vue-compatible wrapper around Chart.js
  • A small Vue state store, implemented either with Pinia or native reactive state

6.2 Analytics Dashboard page

The dashboard must contain five metric blocks. Every block must display:

  • The metric name.
  • The latest value.
  • A time-series chart showing how the value changed during the last hour.

Expected layout:

----------------------------------------------------
| Online Drivers       | Ride Requests             |
| latest value         | latest value              |
| [last-hour chart]    | [last-hour chart]         |
----------------------------------------------------
| Accepted Requests    | Cancelled Requests        |
| latest value         | latest value              |
| [last-hour chart]    | [last-hour chart]         |
----------------------------------------------------
| Drivers Waiting                                   |
| latest value                                      |
| [last-hour chart]                                 |
----------------------------------------------------

The charts may connect observed values using normal line interpolation. No advanced smoothing, forecasting, or aggregation is required.

6.3 Metrics Settings page

The page must contain one numeric input for each of the five metrics and one submit button.

FieldInput behavior
Online DriversInteger, minimum 0
Ride RequestsInteger, minimum 0
Accepted RequestsInteger, minimum 0
Cancelled RequestsInteger, minimum 0
Drivers WaitingInteger, minimum 0

6.4 Frontend state behavior

The frontend maintains the latest known value for all five metrics. When the Settings page is first loaded:

  1. It requests the latest snapshot from the backend.
  2. If a snapshot exists, the store is initialized using those values.
  3. If no snapshot exists, all five values default to 0.

When the user changes only one input, unchanged metrics keep their values in the frontend store. On submit, the frontend sends the full snapshot rather than sending null values.

Example: if only online_drivers changes from 25 to 40, the request still includes the current values of ride requests, accepted requests, cancelled requests, and waiting drivers.

7. Backend requirements

7.1 Technology

  • Python
  • FastAPI
  • Pydantic request and response models
  • Kafka producer client
  • HTTP client or Pinot-compatible client for analytical queries

7.2 Responsibilities

The backend has two primary responsibilities:

  1. Ingestion path: validate a submitted complete metric snapshot and publish it to Kafka.
  2. Query path: query Pinot for current metric values and one-hour history, then return JSON to the Vue dashboard.

FastAPI should remain stateless. The frontend owns temporary editable state; Pinot owns persisted analytical history.

8. Kafka event model

Each successful settings submission produces exactly one complete snapshot event.

{
  "event_id": "uuid",
  "timestamp": "2026-10-11T08:30:00Z",
  "zone_id": "ZONE_1",
  "online_drivers": 75,
  "ride_requests": 100,
  "accepted_requests": 60,
  "cancelled_requests": 15,
  "waiting_drivers": 20
}

Required properties

  • event_id — unique identifier generated by the backend.
  • timestamp — backend-generated UTC event timestamp.
  • zone_id — fixed to the demo zone identifier, initially ZONE_1.
  • All five metrics — always present and non-null.

The Kafka topic may be named something explicit such as ride-metrics-snapshots.

9. Apache Pinot requirements

9.1 Table type

The application should use a Pinot real-time table consuming directly from the Kafka topic.

9.2 Data stored

Pinot stores every snapshot event. Existing historical rows are not overwritten. This append-only model enables last-hour time-series visualization.

9.3 Query patterns

Pinot must support at least the following query patterns:

  • Retrieve the latest snapshot for ZONE_1.
  • Retrieve the last hour of values ordered by timestamp.
  • Return the five current values for dashboard cards.
  • Return timestamp/value pairs for each metric chart.
Since this is a learning project, optimization beyond what is needed for responsive local queries is not required. Schema/index decisions should remain simple and understandable.

10. API requirements

10.1 Submit metric snapshot

POST /api/metrics

Request:

{
  "zone_id": "ZONE_1",
  "online_drivers": 75,
  "ride_requests": 100,
  "accepted_requests": 60,
  "cancelled_requests": 15,
  "waiting_drivers": 20
}

Behavior:

  1. Validate the payload.
  2. Generate event_id and timestamp.
  3. Publish one event to Kafka.
  4. Return a success response when the event is accepted for publishing.

10.2 Get current metrics

GET /api/metrics/current?zone_id=ZONE_1

Returns the most recently ingested snapshot from Pinot. If Pinot contains no snapshots yet, the backend returns a valid zero-valued snapshot.

10.3 Get dashboard history

GET /api/metrics/history?zone_id=ZONE_1&window=1h

Returns historical timestamped metric observations for the previous hour. The response may contain all five metric series in one payload to reduce frontend requests.

10.4 Optional combined dashboard endpoint

During implementation, it is acceptable to expose a combined endpoint such as GET /api/dashboard that returns current values plus one-hour history in a single response, if this keeps the frontend simpler.

11. Business rules and validation

The backend is the final authority for validating submitted data.

RuleRequirement
Non-negative values All metrics must be integers greater than or equal to 0.
Accepted + cancelled accepted_requests + cancelled_requests <= ride_requests
Waiting drivers waiting_drivers <= online_drivers
Pending requests Allowed. Ride requests do not need to equal accepted + cancelled.
Complete snapshot All five metrics must be present in every accepted request.
Zone Only the configured demo zone is accepted in v1.

The frontend should also provide immediate input-level validation for user convenience, but backend validation remains mandatory.

12. Real-time behavior

Dashboard polling

The Vue dashboard polls FastAPI at a short fixed interval. A default interval of approximately 1–2 seconds is recommended for the local demo.

Expected lifecycle:

  1. User submits a new snapshot.
  2. FastAPI publishes it to Kafka.
  3. Pinot consumes and stores the event.
  4. The next dashboard poll queries Pinot through FastAPI.
  5. The metric card and corresponding chart reflect the new value.

WebSockets and Server-Sent Events are explicitly out of scope for v1.

13. Error handling

  • Invalid numeric input should produce a clear validation message.
  • Business-rule violations should return HTTP 422 or HTTP 400 with a readable explanation.
  • Kafka publishing failures should return an error and must not be reported as successful.
  • Pinot query failures should return an appropriate backend error and the frontend should show a non-blocking error state.
  • If history is empty, charts should render an empty state rather than fail.
  • If no previous snapshot exists, current metrics should default to zero.

14. Local development and infrastructure

The entire demo should run locally using Docker Compose where practical.

Expected services:

  • Kafka
  • Apache Pinot components required for a local real-time table
  • FastAPI backend
  • Vue frontend

It is acceptable during early development to run Vue and/or FastAPI directly on the host while Kafka and Pinot run in containers. The final local setup should be easy to start and document.

Configuration

Hostnames, ports, Kafka topic name, Pinot broker URL, and polling interval should be configurable using environment variables or simple configuration files.

15. Acceptance criteria

  1. The project starts locally with documented commands.
  2. The Settings page shows five numeric inputs and a submit button.
  3. All inputs reject negative values.
  4. The backend rejects accepted + cancelled > ride_requests.
  5. The backend rejects waiting_drivers > online_drivers.
  6. Submitting a settings form creates one complete Kafka snapshot event.
  7. No metric in the event is null.
  8. Pinot consumes the event from Kafka and persists it in the real-time table.
  9. The Dashboard displays all five latest values.
  10. The Dashboard displays a one-hour history chart for every metric.
  11. The Dashboard updates through polling without requiring a page refresh.
  12. Refreshing the Settings page initializes values from the latest Pinot snapshot.
  13. If Pinot contains no data, the application initializes all metrics to zero.
  14. Only one zone is used, while zone_id remains part of the event and API model.
  15. No PostgreSQL database, authentication flow, or production-grade user management is introduced.
Definition of done: A developer can change one or more metrics from the Settings page and see the new values and their historical evolution appear on the Dashboard after the Kafka → Pinot ingestion path completes.
