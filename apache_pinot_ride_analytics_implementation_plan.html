1. Implementation summary

The application stores no mutable business row in a traditional database. Every settings submission becomes an immutable, timestamped snapshot event. Kafka transports the event; Pinot consumes it and stores the historical sequence. The latest event acts as the current state.

Key decision: the frontend sends all five metric values on each write. FastAPI never fills missing metrics by querying Pinot. Pinot is queried only for reads and for initializing the frontend after page load.

The implementation should be completed in this order:

  1. Run Kafka + Pinot locally.
  2. Create Kafka topic.
  3. Create Pinot schema and REALTIME table.
  4. Manually produce a test Kafka event and verify Pinot ingestion.
  5. Build FastAPI Pinot query client.
  6. Build FastAPI Kafka producer and write endpoint.
  7. Build current/history APIs.
  8. Build Vue Settings page.
  9. Build Vue Dashboard page with polling and charts.
  10. Add automated tests and developer documentation.

4. Implementation phases

1

Infrastructure and data path

Start Kafka and Pinot, create the topic, schema, and table, then verify one manually produced event becomes queryable.

Exit criterion: SELECT * FROM ride_metrics ORDER BY event_timestamp DESC LIMIT 1 returns the manual event.
2

Backend read path

Implement Pinot HTTP querying, response parsing, current snapshot endpoint, and one-hour history endpoint.

Exit criterion: curl against FastAPI returns real data read from Pinot.
3

Backend write path

Implement full snapshot validation, event enrichment, Kafka publishing, and errors.

Exit criterion: POSTing metrics produces a new row visible in Pinot.
4

Settings UI

Initialize state from current metrics, validate inputs, submit a complete snapshot, and display success/error feedback.

5

Dashboard UI

Render five cards and five last-hour line charts. Poll backend every two seconds.

6

Tests, documentation, polish

Add automated tests, health checks, startup instructions, and debugging commands.

5. Local infrastructure

Keep infrastructure explicit rather than relying permanently on Pinot QuickStart. This makes the Kafka → Pinot relationship visible and easier to debug. It is still fine to use QuickStart during initial exploration.

5.2 Docker Compose strategy

Use Docker Compose for Kafka and Pinot. The exact Kafka image can be swapped if desired; the application contract is simply that the broker is reachable internally as kafka:9092 and externally as localhost:9092. Pinot's table config must use the internal Docker hostname.

Important networking rule: inside the Pinot container, localhost:9092 means the Pinot container itself, not Kafka. The Pinot stream config should therefore use kafka:9092.

7. Pinot schema

File: infra/pinot/ride-metrics-schema.json

{
  "schemaName": "ride_metrics",
  "enableColumnBasedNullHandling": true,
  "dimensionFieldSpecs": [
    {"name": "event_id", "dataType": "STRING", "notNull": true},
    {"name": "zone_id", "dataType": "STRING", "notNull": true}
  ],
  "metricFieldSpecs": [
    {"name": "online_drivers", "dataType": "INT", "notNull": true},
    {"name": "ride_requests", "dataType": "INT", "notNull": true},
    {"name": "accepted_requests", "dataType": "INT", "notNull": true},
    {"name": "cancelled_requests", "dataType": "INT", "notNull": true},
    {"name": "waiting_drivers", "dataType": "INT", "notNull": true}
  ],
  "dateTimeFieldSpecs": [
    {
      "name": "event_timestamp",
      "dataType": "LONG",
      "format": "1:MILLISECONDS:EPOCH",
      "granularity": "1:MILLISECONDS"
    }
  ]
}

Why this shape?

  • event_id is an event identifier.
  • zone_id is a filterable dimension.
  • The five numeric values are Pinot metric fields.
  • event_timestamp is a datetime field used for ordering and rolling one-hour filters.

Compatibility note: Pinot documentation also shows newer stream configuration under ingestionConfig.streamIngestionConfig. If your 1.5.1 image rejects the legacy placement above, move the same stream keys into that structure. The project should keep the final working JSON committed to Git.

Indexes

  • Inverted index on zone_id: supports zone filtering.
  • Range index on event_timestamp: supports rolling time-range filters.
  • No star-tree, bloom filter, or advanced pre-aggregation is needed in v1.

11.3 Models and business validation

from pydantic import BaseModel, Field, model_validator


class MetricsSnapshotInput(BaseModel):
    zone_id: str
    online_drivers: int = Field(ge=0)
    ride_requests: int = Field(ge=0)
    accepted_requests: int = Field(ge=0)
    cancelled_requests: int = Field(ge=0)
    waiting_drivers: int = Field(ge=0)

    @model_validator(mode="after")
    def validate_business_rules(self):
        if self.accepted_requests + self.cancelled_requests > self.ride_requests:
            raise ValueError(
                "accepted_requests + cancelled_requests must be <= ride_requests"
            )

        if self.waiting_drivers > self.online_drivers:
            raise ValueError(
                "waiting_drivers must be <= online_drivers"
            )

        if self.zone_id != "ZONE_1":
            raise ValueError("Only ZONE_1 is supported")

        return self


class MetricsEvent(MetricsSnapshotInput):
    event_id: str
    event_timestamp: int

12. Hot code region: publishing Kafka events

Create one Kafka producer at application startup and reuse it.

import json
from aiokafka import AIOKafkaProducer


class MetricsKafkaProducer:
    def __init__(self, bootstrap_servers: str, topic: str):
        self._bootstrap_servers = bootstrap_servers
        self._topic = topic
        self._producer: AIOKafkaProducer | None = None

    async def start(self) -> None:
        self._producer = AIOKafkaProducer(
            bootstrap_servers=self._bootstrap_servers,
            value_serializer=lambda value: json.dumps(value).encode("utf-8"),
            acks="all",
        )
        await self._producer.start()

    async def stop(self) -> None:
        if self._producer:
            await self._producer.stop()

    async def publish(self, event: dict) -> None:
        if not self._producer:
            raise RuntimeError("Kafka producer is not started")

        await self._producer.send_and_wait(
            self._topic,
            value=event,
        )

FastAPI lifespan

from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    await kafka.start()
    app.state.kafka = kafka
    app.state.pinot = pinot
    yield
    await kafka.stop()
    await pinot.close()

Write endpoint

from time import time
from uuid import uuid4

from fastapi import APIRouter, HTTPException, Request

router = APIRouter(prefix="/api/metrics", tags=["metrics"])


@router.post("", status_code=202)
async def update_metrics(payload: MetricsSnapshotInput, request: Request):
    event = MetricsEvent(
        event_id=str(uuid4()),
        event_timestamp=int(time() * 1000),
        **payload.model_dump(),
    )

    try:
        await request.app.state.kafka.publish(event.model_dump())
    except Exception as exc:
        raise HTTPException(
            status_code=503,
            detail="Unable to publish metrics event to Kafka",
        ) from exc

    return {
        "status": "accepted",
        "event_id": event.event_id,
        "event_timestamp": event.event_timestamp,
    }
202 Accepted means the event was successfully published to Kafka. Pinot ingestion is asynchronous, so the new value may appear on the next dashboard poll rather than in the same request.

13. Hot code region: querying Apache Pinot

Use the Pinot Broker HTTP endpoint /query/sql and centralize response parsing.

import httpx


class PinotQueryError(RuntimeError):
    pass


class PinotClient:
    def __init__(self, broker_url: str):
        self._url = f"{broker_url.rstrip('/')}/query/sql"
        self._client = httpx.AsyncClient(timeout=3.0)

    async def close(self) -> None:
        await self._client.aclose()

    async def query(self, sql: str) -> list[dict]:
        response = await self._client.post(
            self._url,
            json={"sql": sql},
        )
        response.raise_for_status()
        payload = response.json()

        exceptions = payload.get("exceptions") or []
        if exceptions:
            raise PinotQueryError(str(exceptions))

        result_table = payload.get("resultTable")
        if not result_table:
            return []

        columns = result_table["dataSchema"]["columnNames"]
        rows = result_table.get("rows", [])

        return [
            dict(zip(columns, row, strict=True))
            for row in rows
        ]

Combined dashboard endpoint

import asyncio

@router.get("/dashboard")
async def dashboard(request: Request):
    pinot = request.app.state.pinot

    current_rows, history_rows = await asyncio.gather(
        pinot.query(CURRENT_SQL),
        pinot.query(HISTORY_SQL),
    )

    current = current_rows[0] if current_rows else ZERO_STATE

    return {
        "current": current,
        "history": history_rows,
    }
One combined dashboard call is preferable to five independent history calls. All five metrics are columns of the same snapshot row.

15.2 Pinia metrics store

import { defineStore } from "pinia";
import { ref } from "vue";
import { getCurrentMetrics, updateMetrics } from "../services/api";

export const useMetricsStore = defineStore("metrics", () => {
  const onlineDrivers = ref(0);
  const rideRequests = ref(0);
  const acceptedRequests = ref(0);
  const cancelledRequests = ref(0);
  const waitingDrivers = ref(0);

  function applySnapshot(snapshot) {
    onlineDrivers.value = snapshot.online_drivers;
    rideRequests.value = snapshot.ride_requests;
    acceptedRequests.value = snapshot.accepted_requests;
    cancelledRequests.value = snapshot.cancelled_requests;
    waitingDrivers.value = snapshot.waiting_drivers;
  }

  async function initialize() {
    applySnapshot(await getCurrentMetrics());
  }

  async function submit() {
    return updateMetrics({
      zone_id: "ZONE_1",
      online_drivers: onlineDrivers.value,
      ride_requests: rideRequests.value,
      accepted_requests: acceptedRequests.value,
      cancelled_requests: cancelledRequests.value,
      waiting_drivers: waitingDrivers.value,
    });
  }

  return {
    onlineDrivers,
    rideRequests,
    acceptedRequests,
    cancelledRequests,
    waitingDrivers,
    initialize,
    submit,
  };
});

15.3 API client

const API_BASE = import.meta.env.VITE_API_BASE_URL ?? "http://localhost:8000";

export async function getCurrentMetrics() {
  const response = await fetch(`${API_BASE}/api/metrics/current`);
  if (!response.ok) throw new Error("Failed to load current metrics");
  return response.json();
}

export async function updateMetrics(payload) {
  const response = await fetch(`${API_BASE}/api/metrics`, {
    method: "POST",
    headers: {"Content-Type": "application/json"},
    body: JSON.stringify(payload),
  });

  const body = await response.json();
  if (!response.ok) {
    throw new Error(body.detail ?? "Failed to update metrics");
  }
  return body;
}

export async function getDashboard() {
  const response = await fetch(`${API_BASE}/api/dashboard`);
  if (!response.ok) throw new Error("Failed to load dashboard");
  return response.json();
}

16. Dashboard polling and charts

16.1 Polling loop

import { onMounted, onUnmounted, ref } from "vue";
import { getDashboard } from "../services/api";

const dashboard = ref(null);
const error = ref(null);
let timer = null;
let isRefreshing = false;

async function refresh() {
  if (isRefreshing) return;

  isRefreshing = true;
  try {
    dashboard.value = await getDashboard();
    error.value = null;
  } catch (err) {
    error.value = err.message;
  } finally {
    isRefreshing = false;
  }
}

onMounted(async () => {
  await refresh();
  timer = window.setInterval(refresh, 2000);
});

onUnmounted(() => {
  if (timer) window.clearInterval(timer);
});

16.2 Convert Pinot history into chart series

function toSeries(history, field) {
  return history.map((row) => ({
    x: row.event_timestamp,
    y: row[field],
  }));
}

Each metric card should show the latest number above a line chart. The line joins submitted snapshot points in chronological order.

18. Testing strategy

18.1 Unit tests

  • All-zero snapshot is valid.
  • Negative metric fails.
  • accepted + cancelled == ride_requests is valid.
  • accepted + cancelled > ride_requests fails.
  • waiting_drivers == online_drivers is valid.
  • waiting_drivers > online_drivers fails.
  • Pinot tabular response maps correctly into dictionaries.

18.2 Backend API tests

  • Valid POST → 202 and one Kafka publish.
  • Invalid POST → 422 and zero Kafka publishes.
  • Kafka failure → 503.
  • No Pinot row → current endpoint returns zeros.
  • Dashboard endpoint returns current + history.

20. Performance choices

One dashboard HTTP call

Current state plus all five histories are fetched together.

Two Pinot queries

Latest row and history query execute concurrently.

One Kafka partition

Simple ordering for a one-zone, low-volume demo.

Raw history points

No time bucketing required for manually submitted snapshots.

21. Semantics of “current state”

Pinot remains append-only. Changing a value creates a newer snapshot rather than updating the previous row:

10:00 → online_drivers = 20
10:05 → online_drivers = 30

The current state is therefore the values contained in the row with the newest event_timestamp.
