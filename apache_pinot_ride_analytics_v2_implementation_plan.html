Implementation Plan v2 — Event-Driven Apache Pinot Ride Analytics Lab

Full implementation blueprint for converting the existing snapshot demo into a high-throughput, event-driven Apache Pinot lab while preserving v1.

v1 preservedoperations_REALTIME Generator UI50–1000 events/sec presets Single zone: ZONE_1

1. Goal and design principles

v2 keeps the current snapshot-based demo intact, but adds a separate event-driven lab. The new path stores immutable user, ride, and driver events in Kafka/Pinot and derives dashboard values with Pinot analytics instead of storing precomputed counters.

Core learning objective: continuously ingest hundreds or thousands of events per second while Pinot serves low-latency filters, counts, time buckets, distinct counts, and latest-state queries.
  • Keep v1 untouched for comparison.
  • Events are append-only.
  • The generator creates only valid state transitions.
  • Pinot stores events, not dashboard counters.
  • Every Start creates a fresh simulation run.
  • The generator runs in FastAPI; Vue only controls it.

4. Event model

EventMeaning
RIDE_REQUESTEDUser creates a ride request.
RIDE_ACCEPTEDA waiting driver accepts it.
RIDE_CANCELLEDUser cancels before acceptance.
RIDE_COMPLETEDAccepted ride finishes.
DRIVER_CONNECTEDOffline driver connects.
DRIVER_WAITINGOnline driver is unassigned.
DRIVER_ASSIGNEDWaiting driver is assigned.
DRIVER_DISCONNECTEDWaiting driver disconnects.

Common event envelope

{
  "event_id": "uuid",
  "event_version": 1,
  "simulation_id": "sim-...",
  "sequence_number": 18432,
  "event_timestamp": 1791712800123,
  "event_type": "RIDE_ACCEPTED",
  "zone_id": "ZONE_1",
  "user_id": "user-004211",
  "driver_id": "driver-000482",
  "ride_id": "ride-007844"
}

simulation_id is required because old runs remain in Pinot. Every dashboard query filters on the active simulation.

sequence_number is a monotonically increasing per-run number used to break timestamp ties at high event rates.

5. State machines and invariants

User

IDLE
  └─ RIDE_REQUESTED → WAITING_FOR_DRIVER
       ├─ RIDE_CANCELLED → IDLE
       └─ RIDE_ACCEPTED → IN_RIDE
                            └─ RIDE_COMPLETED → IDLE

Driver

OFFLINE
  └─ DRIVER_CONNECTED → WAITING
       ├─ DRIVER_DISCONNECTED → OFFLINE
       └─ DRIVER_ASSIGNED → ASSIGNED
                              └─ ride completion → WAITING

Ride

REQUESTED
  ├─ RIDE_CANCELLED → CANCELLED
  └─ RIDE_ACCEPTED → ACCEPTED
                       └─ RIDE_COMPLETED → COMPLETED
  1. A user has at most one active ride.
  2. A driver is assigned to at most one active ride.
  3. Only IDLE users may request rides.
  4. Only REQUESTED rides may be accepted or cancelled.
  5. Cancellation after acceptance is out of scope.
  6. Accept requires a WAITING driver.
  7. Only WAITING drivers may disconnect.
  8. ASSIGNED drivers cannot disconnect.
  9. Completing a ride returns the user to IDLE and driver to WAITING.
  10. Online drivers = WAITING + ASSIGNED.
  11. Waiting drivers = drivers whose latest state is WAITING.
  12. Active users = users whose latest ride state is REQUESTED or ACCEPTED.

6. Generator controls and lifecycle

Frontend-configurable values

SettingDefaultAllowed
User pool10,000Positive integer
Driver pool2,000Positive integer
Target Kafka events/sec25050, 100, 250, 500, 1000, custom
ZoneZONE_1Fixed for v2

Start

  1. Reject Start if already active.
  2. Create a new simulation_id.
  3. Reset sequence number.
  4. Create fresh user and driver pools.
  5. All users begin IDLE and all drivers begin OFFLINE.
  6. Enter WARMING_UP and connect drivers through normal emitted events.
  7. Move to RUNNING once a useful waiting-driver pool exists.

Stop

  • Stop scheduling new actions.
  • Flush already-created Kafka sends.
  • Mark status STOPPED.
  • Keep last runtime stats visible.
  • Next Start creates a completely fresh run with a new simulation ID.
  • Do not delete old Pinot events.

Generate valid business actions, never random event names.

request_ride       30

These are weights, not strict percentages. Invalid actions are excluded. State correctness always wins over desired distribution.

8. Throughput model

PresetEvents/hourPurpose
50/s180,000Smoke load
100/s360,000Low sustained load
250/s900,000Recommended first meaningful run
500/s1.8MGood local Pinot lab load
1000/s3.6MTry only after observing resources

For an i7 / 16 GB RAM laptop, begin at 100–250 events/sec. Increase gradually while watching memory, CPU, Kafka/Pinot lag, and query latency.

Rate scheduling

tick = 100 ms
budget += target_eps * 0.1

while enough event budget:
    choose a valid action
    estimate action cost (1 or 2 Kafka events)
    if cost fits budget:
        execute action
        enqueue events
        budget -= cost

publish the tick batch
sleep until next tick
The UI rate is Kafka events/sec, not actions/sec, because some actions emit two events.

11. Pinot analytical queries

Every query for the active lab run must filter by simulation_id.

Ride event counts over the last 60 seconds

SELECT event_type, COUNT(*) AS event_count
FROM operations
WHERE simulation_id = 'SIMULATION_ID'
  AND event_timestamp >= ago('PT60S')
  AND event_type IN (
    'RIDE_REQUESTED','RIDE_ACCEPTED',
    'RIDE_CANCELLED','RIDE_COMPLETED'
  )
GROUP BY event_type

Ride lifecycle per minute for the last hour

SELECT
  DATETIMECONVERT(
    event_timestamp,
    '1:MILLISECONDS:EPOCH',
    '1:MILLISECONDS:EPOCH',
    '1:MINUTES'
  ) AS time_bucket,
  event_type,
  COUNT(*) AS event_count
FROM operations
WHERE simulation_id = 'SIMULATION_ID'
  AND event_timestamp >= ago('PT1H')
  AND event_type IN (
    'RIDE_REQUESTED','RIDE_ACCEPTED',
    'RIDE_CANCELLED','RIDE_COMPLETED'
  )
GROUP BY time_bucket, event_type
ORDER BY time_bucket ASC

Latest driver state

SELECT latest_driver_event, COUNT(*) AS drivers
FROM (
  SELECT
    driver_id,
    ARG_MAX(event_timestamp, sequence_number, event_type)
      AS latest_driver_event
  FROM operations
  WHERE simulation_id = 'SIMULATION_ID'
    AND driver_id IS NOT NULL
    AND event_type IN (
      'DRIVER_CONNECTED','DRIVER_WAITING',
      'DRIVER_ASSIGNED','DRIVER_DISCONNECTED'
    )
  GROUP BY driver_id
)
GROUP BY latest_driver_event

Interpret:

waiting_drivers = DRIVER_WAITING
assigned_drivers = DRIVER_ASSIGNED
online_drivers = DRIVER_WAITING + DRIVER_ASSIGNED + DRIVER_CONNECTED

Active users

SELECT COUNT(*) AS active_users
FROM (
  SELECT
    user_id,
    ARG_MAX(event_timestamp, sequence_number, event_type)
      AS latest_ride_event
  FROM operations
  WHERE simulation_id = 'SIMULATION_ID'
    AND user_id IS NOT NULL
    AND event_type IN (
      'RIDE_REQUESTED','RIDE_ACCEPTED',
      'RIDE_CANCELLED','RIDE_COMPLETED'
    )
  GROUP BY user_id
)
WHERE latest_ride_event IN ('RIDE_REQUESTED','RIDE_ACCEPTED')

Observed users

SELECT COUNT(DISTINCT user_id)
FROM operations
WHERE simulation_id = 'SIMULATION_ID'
  AND user_id IS NOT NULL

Actual Pinot-ingested event rate

SELECT
  DATETIMECONVERT(
    event_timestamp,
    '1:MILLISECONDS:EPOCH',
    '1:MILLISECONDS:EPOCH',
    '10:SECONDS'
  ) AS bucket,
  COUNT(*) / 10.0 AS events_per_second
FROM operations
WHERE simulation_id = 'SIMULATION_ID'
  AND event_timestamp >= ago('PT10M')
GROUP BY bucket
ORDER BY bucket ASC
The latest-state queries use subqueries and may require Pinot's multi-stage query engine depending on the installed version. Keep this in the Pinot client query options.

Event factory

def build_event(sim, event_type, *,
                user_id=None, driver_id=None, ride_id=None):
    sim.sequence_number += 1
    return {
        "event_id": str(uuid4()),
        "event_version": 1,
        "simulation_id": sim.simulation_id,
        "sequence_number": sim.sequence_number,
        "event_timestamp": int(time() * 1000),
        "event_type": event_type,
        "zone_id": "ZONE_1",
        "user_id": user_id,
        "driver_id": driver_id,
        "ride_id": ride_id,
    }

Accept ride

def accept_ride(sim):
    ride = sim.random_requested_ride()
    driver = sim.random_waiting_driver()
    if ride is None or driver is None:
        return []

    user = sim.users[ride.user_id]
    ride.state = RideState.ACCEPTED
    ride.driver_id = driver.driver_id
    user.state = UserState.IN_RIDE
    driver.state = DriverState.ASSIGNED
    driver.active_ride_id = ride.ride_id

    return [
        build_event(sim, "RIDE_ACCEPTED",
            user_id=user.user_id,
            driver_id=driver.driver_id,
            ride_id=ride.ride_id),
        build_event(sim, "DRIVER_ASSIGNED",
            user_id=user.user_id,
            driver_id=driver.driver_id,
            ride_id=ride.ride_id),
    ]

Complete ride

def complete_ride(sim):
    ride = sim.random_accepted_ride()
    if ride is None:
        return []

    user = sim.users[ride.user_id]
    driver = sim.drivers[ride.driver_id]

    ride.state = RideState.COMPLETED
    user.state = UserState.IDLE
    user.active_ride_id = None
    driver.state = DriverState.WAITING
    driver.active_ride_id = None

    return [
        build_event(sim, "RIDE_COMPLETED",
            user_id=user.user_id,
            driver_id=driver.driver_id,
            ride_id=ride.ride_id),
        build_event(sim, "DRIVER_WAITING",
            driver_id=driver.driver_id,
            ride_id=ride.ride_id),
    ]

Kafka batch publishing

async def publish_batch(self, events):
    deliveries = []
    for event in events:
        delivery = await self._producer.send(
            self._topic,
            value=event,
        )
        deliveries.append(delivery)

    if deliveries:
        await asyncio.gather(*deliveries)

    acks="all",
    linger_ms=5,

17. Implementation phases

  1. v2 data plane: create topic, schema, REALTIME table; manually publish every event type and verify Pinot.
  2. Simulation model: entities, pools, indexes, invariants, and actions with unit tests. No background loop yet.
  3. Scheduler: event-budget rate limiter, simulation lifecycle, Kafka batch publish, Start/Stop.
  4. Generator API/UI: pool sizes, presets, status, Start/Stop.
  5. Pinot analytics: recent counts, time buckets, latest driver state, active users, observed users, event rate.
  6. Dashboard v2: cards/charts and combined endpoint.
  7. Benchmark/tune: 50 → 100 → 250 → 500 → 1000 events/sec.
Important: Codex should complete and verify each phase before moving to the next.

18. Test strategy

State-machine tests

  • A non-IDLE user cannot request another ride.
  • An ACCEPTED ride cannot be cancelled.
  • Accept requires REQUESTED ride + WAITING driver.
  • A driver cannot serve two active rides.
  • ASSIGNED drivers cannot disconnect.
  • Completion restores user IDLE and driver WAITING.
  • Two-event transitions have increasing sequence numbers.

Generator tests

  • Start creates a unique simulation ID.
  • Start while already running returns conflict.
  • Stop flushes pending sends and halts scheduling.
  • Restart creates a fresh pool and new simulation ID.
  • Measured throughput settles within a reasonable tolerance, e.g. ±10%.

Pinot tests

  • All eight event types ingest.
  • simulation_id isolates runs.
  • Latest driver state matches known sequences.
  • Active-user query matches known ride lifecycles.
  • Time-bucket query returns aggregates instead of raw rows.

Reconciliation

generator waiting drivers ≈ Pinot waiting drivers
generator assigned drivers ≈ Pinot assigned drivers
generator active users ≈ Pinot active users

Short differences are expected because ingestion is asynchronous. Persistent differences mean an event or query bug.

19. Benchmark procedure

  1. 50/s for 5 minutes — correctness.
  2. 100/s for 10 minutes.
  3. 250/s for 15–30 minutes.
  4. 500/s for 15–30 minutes.
  5. 1000/s only if memory and ingestion freshness remain healthy.

22. Technical notes

Apache Pinot supports Kafka-backed REALTIME ingestion where streamed records become queryable within seconds. Its aggregation functions include latest-value patterns such as LASTWITHTIME and ARG_MAX, which fit append-only state-transition analytics.

Before final commit, validate the exact table-config and multi-stage query options against the Pinot version running locally. Keep the final working JSON configs in source control.
